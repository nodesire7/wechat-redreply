# 微信接入红色问答 · Rust 独立版

通过 OneBot11 让现有 RedReply 私聊、群聊插件处理微信消息。Rust 单个 EXE，运行不需要 Python、虚拟环境、Rust 工具链或另装 VC 运行库。界面使用本机 WebView2 Runtime 渲染本地 HTML/CSS；Windows 11 自带，Windows 10/Server 2019 需安装 Evergreen Runtime，缺失时自动回退到原生界面。仍需要 Windows 和已登录的微信客户端。

从 [Releases](https://github.com/nodesire7/wechat-redreply/releases) 下载 Windows x64 完整便携包。首次使用见 [QUICKSTART.md](QUICKSTART.md)，包括自聊中转名称、本地/远程连接和升级步骤。分发包不带个人配置或数据，首次启动自动生成独立 Token。

## 使用

可选 AI 已加入“AI 模型”页面：支持多套云端/本地 Chat Completions 兼容配置、保存并测试、异步任务和短期上下文。由 RedReply 显式调用，不改变原有关键词插件；生成、入队和送达分别记录。接入示例及完整动作见 [AI 配置与 RedReply 接入](redlang/AI.md)。首次使用默认关闭，无模型 Key 也能继续使用原有全部功能。

双击 `WechatRedReply.exe` 默认进入“账号与接入”。在同一页绑定已登录的微信窗口并配置 RedReply 连接，再到“接管范围”选择白名单。绑定、加入白名单、复制接入地址和启动都会保存相应设置，减少单独保存步骤。关闭设置窗口后监听继续运行；通过设置窗口停止监听。

界面使用 WebView2 渲染，保留红白绿配色与明暗主题，参考 Motrix 的侧栏和内嵌工作区组织任务；账号绑定在上、连接表单在下。默认窗口1160×780，最小960×680。表单、日志与队列都是内嵌本地页面，不加载公网资源。同机 RedReply 使用 `127.0.0.1`，远程 RedReply 使用微信机器的可达地址；在 GUI 复制完整 OneBot 接入地址后填入 RedReply。修改连接或绑定后按需自动重启；白名单、轮询间隔和撤回上限热更新。合并转发优先自动识别本账号自聊，只有识别失败或需要指定名称时才到高级设置填写。

“日志与对话”包含全部、对话记录、协议明细、运行状态四种视图，可暂停刷新和复制当前内容。启动时载入每个白名单会话近期15条文字历史，新消息实时记录原文、成员、会话、消息ID、回复内容、回包与耗时。图片只记录摘要，认证信息隐藏。`data/events.jsonl` 按8MB轮转，最多保留当前及两个历史文件；GUI显示最近500项，并在用户向上阅读时保持滚动位置。

“发送队列”独立显示持久化任务、批次、最终发送及撤回结果。已入队只表示内容保存成功，**不等于微信已经发出**。待发送任务可跨程序重启继续；发送过程中断、无法确认的任务标为“待核对”，不盲目重发。

运行状态日志还记录设置窗口的关闭请求、Windows 结束会话、维护命令关闭，以及可观察的微信/设置进程退出码和实际结束时间。退出码不能单独确认是谁关闭了进程；如果未保存句柄且系统已释放进程对象，无法补取历史退出码。

现有 Python 配置可无损导入（不会停止或修改原服务）：

```powershell
.\WechatRedReply.exe --import-python '..\WeChat-AI-AutoReply\wechat_redreply_config.json'
```

导入会保留端口、token、机器人 ID、绑定、白名单和未识别配置字段，并复制接收游标。正式迁移时先停止 Python，复制最新游标，再启动 Rust；同一端口只能保留一个服务。

完整动作映射和限制见 [RedLang 兼容说明](redlang/COMPATIBILITY.md)。默认 GUI 已包含账号、接管范围、队列、日志和高级设置五个实际工作页；不需要跳回旧版界面。私聊与群聊分别搜索和配置。React Bits 用于账号高光、真实状态区与主要操作，队列不会因动画或提交撤回请求就消失。

## 行为

- 数据库/WAL 增量接收保留原文大小写，接收线程不等待发送；同序号消息分别去重，断线时未推送消息保留游标。
- 默认持久化模式：OneBot 请求写入 SQLite WAL 并提交后返回 `message_id`、`batch_id`、`delivery_status=queued`；后台按入队顺序发送，状态查询和撤回登记独立处理。不会因等待微信操作超过 RedReply 的30秒期限而取消积压。待处理最多5000项，保存的请求内容上限256MB；超限或写盘失败明确拒绝，不返回虚假入队成功。原生发送吞吐仍受微信单窗口限制。
- 可用扩展动作 `get_delivery_status` 查询指定 `message_id` 的最终状态；`durable_queue=false` 兼容原同步确认模式。同步模式有128项有界等待和28秒请求预算。
- 私聊与群聊分开路由；群成员身份单独映射。原规则和权限仍由现有 RedReply 决定。
- 支持文字、`base64://` 图片、HTTP(S) 图片和图文混合；后台任务只有在微信数据库出现服务器消息编号后才标为发送成功。图片地址在执行时读取，过期或下载失败在队列中记录。发送已尝试但无法确认时标为待核对，不盲目重发。
- QQ 音乐卡转换：支持带完整元数据的 OneBot `music/custom`、QQ 音乐 JSON，以及微信外层 `appmsg/type=3` XML。`music` 段同时带歌曲 ID 和本次标题、歌手、页面、音频、封面时，优先按本次请求新建卡片，不用同 ID 的旧缓存卡；只有 ID 时才走已有同曲元数据。根据本次请求新建真正的微信音乐卡，不转发缓存里的旧歌。当前已核对的4.2.0.9和4.2.0.12模块使用原生网络任务发送，核对服务端响应中的发送者、目标、客户端标识和完整64位消息ID后才记成功；超时不盲目重发。音乐发送不操作窗口、系统剪贴板、全局键鼠或焦点。已用未缓存的《Youngblood》实测，接收端确认原生音乐卡可播放。
- 该原生音乐发送不会自动写入本机微信的发件数据库；适配器不伪造微信数据库记录。GUI和持久化台账按真实原生网络回执记录，音乐撤回也走原生网络回执，仍受设置上限及120秒硬限制。同一回复中的文字、图片和音乐均可纳入整批撤回。原生后端严格匹配当前微信版本，客户端升级后需重新核验。只有歌曲ID而无元数据的请求，需要已有同曲元数据；尚未实现通用曲库ID查询。卡片分别保留本次歌曲页面与原始音频地址，能核对当前QQ songmid时补齐微信原生播放标识；不提供未经验证的点击模式切换。发送前检查匿名音频响应，登录页或错误页明确失败；微信4.2.0.12的新建卡已由接收端确认可播放；该结果不保证所有音源可播，也不能把网络发送成功当作播放成功。有效播放授权仍由点歌音源提供。当前新建支持QQ音乐来源，其他来源及音乐卡合并转发节点会明确拒绝。
- `record` 发送真正的微信原生语音气泡，目前限已核对的微信4.2.0.12。接受 base64、HTTP(S) 或微信机器可读的绝对路径；内嵌解码器和 SILK 编码器，运行无需 FFmpeg 或 Python。支持 SILK、MP3、WAV、FLAC、AAC/M4A、Ogg/Vorbis，最多10分钟/12MiB，超过60秒按顺序拆成多条语音并共用一次输出回执。已实测1秒语音接收端可播放、服务端确认及延迟30秒后原生撤回。不会用音频文件代替语音，也不伪造本机发件数据库。
- `reply` 段省略，`at` 段转换为可读正文；未实现原生引用、原生群艾特、视频和文件。高级设置可展开查看实际支持与未对齐动作。
- 微信放在所有显示器之外，不最小化；弹窗也受离屏保护。自动收发不访问系统剪贴板、不模拟全局按键、不移动鼠标、不抢前台或键盘焦点。图片通过原生离屏文件选择器发送，原输入草稿暂存并恢复。GUI 的“复制”仅在用户主动点击时写剪贴板。
- 原生合并转发使用账号页设置、已验证属于本账号的自聊会话中转，只选择本批消息，核对唯一收件人。支持跨屏长消息选择；收到微信 `type19` 卡片后，还逐项校验中转消息身份、条数、文字和顺序，全部一致才记录完整发送成功；不降级为普通文字。
- 每次输出单独登记撤回：一次输出拆出的艾特、图片、文字和提示共用一个撤回范围。`reply`、`wechat_batch_id`、`source_message_id` 或 `trigger_id` 只用于追踪整次触发，不把进度提示、正文和后续输出的撤回时间混在一起。对某次输出调用 `delete_msg` / `schedule_delete_msg` 只处理该次输出；不同输出、账号、私聊/群聊严格分开，前一次输出的定时撤回不会阻断或取消后一次输出。
- 长流程插件可调用 `begin_response_batch` / `finish_response_batch`，参数为 `user_id` 或 `group_id` 加 `wechat_batch_id`。这些标记只维护流程追踪和300秒保活，不扩大撤回范围，也不会让前一次输出的撤回请求阻断后一次发送。GUI 状态中的 `open_workflows` 可用于维护前检查，避免在插件查询中途重启。
- 撤回上限默认120秒，设置大于120按120执行，每条按自己的原生发送时间计算。`schedule_delete_msg` 可在尚未发送时登记；该次输出发完后等待指定延迟，同时为逐条撤回预留时间并受最早原生期限约束。已核对的原生后端使用真实服务器消息编号撤回文字、图片和卡片，优先撤回最早发出的部分，不依赖当前视口菜单；提交与确认持久化，未确认结果不重复提交。其他版本保留数据库身份关联的界面路径与有限延迟确认。超时或身份无法核验时明确报错，未确认部分不会冒充已全部撤回。微信4.2.0.12实测临时提示约24–27秒、三段图文约98–102秒全部确认撤回，普通正文保留。
- “自动同意好友申请”强制核对“仅聊天已选中、完整权限已关闭”后才提交，不自动加入回复白名单。微信要求账号安全验证时暂停该功能，消息监听继续；完成验证后点击“安全验证后重试好友申请”。处理记录本地持久化。

单次文字最多4000字符、图片4张；合并转发最多100节点、20条中转消息、256KB节点数据，单行最多3500字符（不会截断磁力链接）。超限明确拒绝。

## 迁移与构建

长期监听会核对绑定聊天窗口的存活、弹窗阻塞与限时响应；微信退出登录后暂停发送并提示重新绑定。未变化的消息查询使用有容量上限的缓存，撤回候选查询使用覆盖索引，避免空闲扫描历史媒体请求。好友申请空闲检查逐步放缓到60秒，普通消息轮询间隔不变。远程桌面中的 GUI 自动使用软件渲染和独立数据目录。此项降低对会话 GPU 的依赖，不能代替 Windows DWM 或显示驱动故障的修复。`--profile-idle` 可只读测量消息数据库、窗口和账号路径检查的耗时与逻辑读取量，不输出聊天内容，不更改游标。

移动整个 EXE 所在目录可保留 `config.json` 和 `data`。只复制 EXE 到空目录会自动生成新配置；原来的 token 应通过配置导入保留。换机器或微信进程重启后需重新绑定。辅助 Rust DLL 内嵌 EXE，首次操作时释放到 `data/runtime`，无网络安装步骤。

开发构建运行 `build.cmd`，需要 Rust MSVC、Visual Studio C++ Build Tools、Windows SDK、CMake、Node.js 22 和 pnpm 10（编译加密依赖）。脚本先构建并同步内嵌 React 页面、运行前端与 Rust 测试，再编译辅助 DLL、内嵌许可证、构建静态 CRT EXE，输出 `dist-build/WechatRedReply.exe`，与正在使用的 `dist` 分开。也可用 `-OutputDirectory` 指定构建目录。依赖锁定于 `Cargo.lock`。运行 `powershell -NoProfile -ExecutionPolicy Bypass -File .\package.ps1` 完成测试、构建和干净打包，输出 ZIP、文件清单和 SHA256；使用明确的文件清单，配置、聊天记录和缓存不会入包。

数据库接收、离屏收发与整批撤回已在微信4.2.0.9验证；原先还验证过4.1.15.13。v0.1.1另在Windows Server 2019和微信4.2.0.12实测了通讯录页恢复、群聊文字、图文拆分发送和对应回执的整批撤回；当前音乐后端包含4.2.0.9和4.2.0.12模块签名，原生语音包含4.2.0.12。Windows 11需在目标机器另行验证。OneBot11 接入无需重构 RedReply；微信升级后的控件或数据库变化需要重新验证。控件异常可双击 `diagnose.cmd` 生成不含令牌和聊天内容的报告，详见 [QUICKSTART.md](QUICKSTART.md)。`--licenses` 可导出内嵌的第三方许可证。
